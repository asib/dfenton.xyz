# Misc entries

For an interactive diagram, add `public/misc/<slug>/diagram.html`, a preview image, and `meta.json`. For CAD entries, use the model format below. The folder name is the URL slug (lowercase letters, digits, and hyphens), and the page is served at `/misc/<slug>/`.

Before adding or changing dependencies, follow the [Cloudflare Pages toolchain instructions in README.md](README.md#cloudflare-pages). Check the actual `bun --version` against the pinned version before any command that writes `bun.lockb`; `packageManager` does not switch an already-installed Bun runtime. Validate dependency changes with a clean frozen install and production build using the same Bun version as Pages.

```json
{
  "title": "Two surfaces, one cutting edge",
  "description": "An interactive exploration of how two surfaces meet to form a cutting edge.",
  "date": "2026-10-18",
  "preview": "preview.webp",
  "previewDark": "preview-dark.webp"
}
```

The Misc page at `/misc/` discovers metadata at build time and lists entries newest first. No registry needs editing. Commit and push to publish through the existing Cloudflare Pages deployment.

Each diagram.html is a standalone document. Keep local assets in its folder and use relative paths. The shared React page provides the title, navigation, and theme toggle. Preserve the sandbox when importing a Codex visualization export. Check mobile layout, light/dark appearance, and controls in an ordinary browser; exports may depend on external CDNs.

The homepage links to `/misc/`. Entry URLs render through the same React shell (Cloudflare Pages SPA fallback), which embeds `diagram.html`. The visualization accepts a `site-theme` message from its same-origin parent and forwards it into the sandbox without resetting interaction state. Its page backgrounds, typography, and general controls use the homepage theme. Semantic diagram colors use their own palettes.

Development previews use the same routes: `/` serves the homepage, `/misc/` lists all entries, and `/misc/tool-tote/` opens the tool tote registered by `public/misc/tool-tote/meta.json`. Preview-server configuration must preserve the homepage rather than redirecting `/` to the item currently being edited. Verify the homepage → Misc → item → Misc → homepage navigation when changing preview configuration.

Misc navigation opts into cross-document View Transitions when reduced motion is off. Each list title and its detail heading share a transition name derived from the entry slug; the browser moves the heading while the surrounding content fades. Links, Back/Forward, scroll restoration, and new-tab behavior remain native browser navigation. Unsupported browsers use ordinary page loads. The entry script blocks first paint and mounts the React shell synchronously so the incoming snapshot contains the page heading. The Vite build hook preserves that script attribute; it does not wait for the lazy CAD viewer, model, compiler, or embedded diagram to load. If the lazy viewer's code fails to load (a refused or dropped request, or a deploy replacing its chunks), `ViewerBoundary` in `MiscPage.tsx` shows a message with a Reload button in its place, instead of the failure unmounting the whole page.

Each list entry includes a small static preview. `preview` is a required image filename in the entry folder (SVG, PNG, WebP, or JPEG); optional `previewDark` selects a separate image when the site’s dark theme is active. Use a representative diagram snapshot, with fine labels removed if they would be unreadable at thumbnail size. The list supplies an accessible title, so preview images use empty alt text. Avoid live iframes in the list.

Keep the embedded document backgrounds transparent, including any nested sandbox, so the site’s theme-toggle hover shadow follows the visible diagram instead of the iframe rectangle. The host and embedded documents must use the same `color-scheme`; browsers can otherwise paint an opaque iframe canvas even with transparent CSS backgrounds. A standalone export can keep its own themed background when opened directly.

Give each diagram explicit light and dark semantic palettes. Define a light value and a dark value for each concept, retaining a recognizable hue family across themes. Choose colors that remain distinguishable from each other, surrounding text, and site accents. Use stronger colors for swatches, lines, and boundaries, and softer versions for large filled areas. Keep the mapping consistent across controls, labels, surfaces, and previews. Retain labels or other cues so meaning does not depend solely on color, and check the full diagram and thumbnail in both themes.

The cutting-edge diagram uses coral for the back (`#b63e4a` / `#ff8c99`), blue for the bevel (`#1769b0` / `#71b7ff`), and teal for the burr (`#087f6b` / `#60d9ba`), with light values first. These are diagram-specific tokens, independent of the site’s primary/accent colors.

## CAD models

CAD entries use the same list, local page URLs, and theme-aware previews. Set `type` to `cad` in metadata; omitted `type` still means an embedded diagram. CAD pages load a shared Three.js viewer only when opened, so the index and diagrams do not load the 3D runtime. They do not need `diagram.html`.

```json
{
  "type": "cad",
  "title": "Parametric magnetic saw guide",
  "description": "A magnetic guide for dovetail and square cuts.",
  "date": "2026-10-18",
  "preview": "preview.webp",
  "previewDark": "preview-dark.webp",
  "model": "magnetic-saw-guide.stl",
  "source": "magnetic-saw-guide.scad",
  "notes": "Describe the model and its intended use.",
  "customizer": {
    "conditions": {
      "dovetail_ratio": { "parameter": "slope_input", "value": "Ratio" },
      "angle_from_square": { "parameter": "slope_input", "value": "Angle" }
    }
  },
  "attribution": {
    "text": "Retain the original source attribution where applicable.",
    "url": "https://example.com/original-design"
  }
}
```

Optional `camera` is a three-number direction from the model's center to the default camera, in model coordinates with Z up; it defaults to `[1.35, 1.8, 1.1]`. Reset view returns to it. Use it when the model's front faces another way, for example `[1.35, -1.8, 1.1]` for a front at −Y.

Keep the STL and previews in the entry folder, along with the original OpenSCAD file when supplied. `model` must be a local lowercase `.stl` filename. Optional `source` is a local lowercase `.scad` filename and is required when `customizer` is present. Optional `sourceUrl` links to an editable CAD document over HTTPS, such as an Onshape document. `notes` and `attribution` are optional. Preserve source comments and attribution. There are no third-party runtime requests: Three.js is bundled with the site and model files are served locally.

The viewer assumes STL coordinates are millimeters with Z up, matching OpenSCAD. It provides orbit/pan/zoom, keyboard rotation/zoom, solid/edge/wireframe modes, and one movable X/Y/Z clipping plane with a flip control. Colored stencil caps show cut material while preserving cavities; these require closed, consistently wound meshes. The first entry is a single solid, so part visibility controls are not shown. View controls do not affect the downloadable solid. Models with `customizer` also expose editable source parameters and regenerate the geometry in the browser.

### Model viewer

The **3D model viewer** at `/misc/model-viewer/` is the viewer with no model of its own: visitors open their own STL, STEP and OpenSCAD files in it. Its metadata sets `"type": "viewer"`, with the usual title, description, date and previews, and optional `notes`. It needs no `model`, `source` or `diagram.html`; its list previews are small SVGs, as there is no fixed model to capture.

`ModelViewer.tsx` (lazy-loaded like `CadViewer`):
- **Opening:** a file can be dropped anywhere on the page, including over a model already open (which it replaces), or chosen with a file picker that also suits keyboards and phones. A "Drop to open" overlay shows while dragging. Window-level drag handlers keep the browser from navigating to a dropped file. A newer file, or Cancel, abandons one still being checked or compiled. Close file empties the viewer.
- **STL files:** a file ending in `.stl` must look like one: a binary STL's size must match its triangle count, or an ASCII STL must start with `solid` and list facets. Otherwise it's refused with a message, and the open model stays.
- **OpenSCAD files:** a `.scad` file compiles once in a worker, as a *lenient* compile: warnings come back with the model instead of failing it, except `include` or `use` files that can't be opened, which leave the design incomplete (only single-file designs work). Syntax errors, failed assertions, 2D designs and empty models are refused with the engine's message after the file's name.
- **Parameters:** `editableParameters` (in `parameters.ts`) keeps the Customizer parameters the panel can edit and write back: numbers (including OpenSCAD literals such as `.5`), text, booleans and choices. Others, such as vectors and reassigned names, keep their values from the file and are named in a note. With any parameters, the file opens with the usual panel. `CadViewer` and `ParametricControls` take it as `local` (a `LocalModel`: the name, text, parameters and default model) instead of loading by URL. Changes recompile leniently, with failed assertions explained as for the site's models. Configurations are saved under `local:<file name>`, and there are no share links, which couldn't carry the file. Downloads are named after the file. The console output and any warnings show under the panel.
- **STEP files:** a `.step` or `.stp` file is read in a worker (`step.ts`, `step.worker.ts`) by OpenCascade, as `occt-import-js` 0.0.23 compiles it to WASM (LGPL-2.1, 7.6 MB). The worker and WASM load only for a STEP file, in a fresh worker each time, and a file still unread after two minutes is given up. Like the OpenSCAD engine's, the worker is built into `assets/workers/`, which `public/_headers` gives a Content-Security-Policy: scripts only from this site, and requests only to it (`connect-src 'self'`), so a compromised engine can't send a visitor's file elsewhere. `'unsafe-eval'` is allowed there, as WebAssembly and OpenCascade's generated bindings need it. Dependabot gives `occt-import-js` PRs of its own rather than batching it, so a new version is reviewed on its own. The reader triangulates each body where the assembly places it; `stepMesh.ts` turns its meshes into one triangle list with a group per body, keeping its normals, so curved faces shade smoothly. Facets on curved faces meet at under 0.2 radians, well inside the 25° at which the viewer draws creases. A STEP file's edges, though, are its B-rep's: each triangle keeps the face it lies in (`faces`, from OpenCascade's per-face triangle ranges, carried to the geometry as `userData.brepFaces`), and `faceEdges` draws the sides where triangles of different faces meet, or that only one triangle has. So tangent edges, such as where a fillet meets a flat face, show as they do in CAD, and a periodic face's seam doesn't. These edges are already whole, so for picking and measuring `edgeTopology` joins them through every point where two meet (`whole`), rather than by the angle and spacing it uses for OpenSCAD's circles, which OpenCascade's unevenly spaced curves defeat: a nut's 18 edges, not 122 pieces. A file whose faces don't cover every triangle falls back to creases. The worker also writes an STL of the triangles, in the file's units, with each facet's own normal rather than the smoothed ones (`faceNormals`), for a Download STL link by the file name. A file OpenCascade can't read is refused with a message, as is one with no solid geometry: an assembly that keeps its parts in other files (`DOCUMENT_FILE`) names them, as only single files open here. `tests/step.test.mjs` reads OpenCascade's own test files, which ship with the package: CAx-IF's assemblies and a cube in three units.
- **No parameters:** without editable parameters there is no panel; a Download STL link sits by the file name, with the console output and warnings below the model.
- **Viewing:** files become object URLs (nothing is uploaded), owned and revoked by `ModelViewer`, and are passed to `CadViewer` as a synthetic CAD entry, memoized per file (a new entry or camera array rebuilds the 3D scene). The viewer remounts per file and opens front-right-top, with every tool: measuring, sections, display modes, the orientation cube and fullscreen.
- **Units:** STL and OpenSCAD files record no units, so a Units choice by the file name (millimetres by default) is kept per file name in `localStorage` (`model-viewer-units`). It reaches `CadViewer` as `fileUnits`: an inch file is scaled by 25.4 to the scene's millimetres, so measurements, bounds and sections are right, and lengths read in inches first. An OpenSCAD file's panel gets the units through `customizer.units`. Downloads keep the file's own units. A change rebuilds the scene from the latest model (`CadViewer` keeps it), so parameter edits survive. A STEP file records its units: its representation context's length unit (`GLOBAL_UNIT_ASSIGNED_CONTEXT`), which may be defined from another, as an inch is from the millimetre (`stepUnits`). Inch and foot files are read in inches and the rest in millimetres, and the file bar shows the unit in place of the menu. Bounds, the section position and the stage label follow any model's units, so the site's inch models show inches first there too.
- **Parts:** visitors' files have no part list, so `CadViewer`'s `genericParts` finds their parts (`fileParts.ts`), numbered in file order, "Part 1", "Part 2" and so on, unless the file names them. A colored OpenSCAD design's parts are its colors, as OpenSCAD groups them, keeping the file's colors in both themes. Otherwise (an STL, or a design in one color) each solid of the STL is a part. A text STL with several `solid … endsolid` blocks lists them (Three's `STLLoader` makes each a geometry group, `stlMesh` reads them), and its blocks are the parts, labelled with their names. A name is the rest of the `solid` line, whitespace collapsed and cut at 60 characters. Blank names, exporters' placeholders (`ascii`, `mesh`, `OpenSCAD_Model`, "Exported from …" and the like) and the first facet that Three's name pattern reads for a nameless block fall back to "Part N", by position. Repeated labels are numbered like pieces ("Leg · 1", "Leg · 2"). Otherwise solids are found as closed surfaces, so bodies a CAD tool exports separately stay apart even where they touch. Triangles join along an edge two of them share. Where more share an edge (touching bodies), they're sorted by angle around it, and a triangle with its material ahead joins the next, which has its material behind; at a shared angle, as for faces that touch, the one ending a body comes first. A piece that isn't closed (a degenerate sliver, say) joins one closed solid it touches at a corner, and open pieces touching none join one another, so a mesh with holes stays whole. OpenSCAD's STLs are unioned, so its touching parts are already one solid. Solids get colors stepped around the wheel by the golden angle, lighter in dark mode. The triangles are regrouped one display group per part, so the legend, part selection, Hide, Isolate, Ghost, opacity and their keys work as for the site's models. Color parts' IDs come from their colors, so a part hidden before a parameter change stays hidden. A file of one solid, or of more than 50 parts, has no legend. A STEP file's parts are its bodies (`bodyParts`), by their names, or the name of the product holding them where a body's own is blank or a placeholder (`SOLID`, `NONE` and the like), or else numbered. Bodies alike in name and color are copies of one part, as an assembly's nuts are: one legend part, with a piece per body ("nut · 3") that can be selected, hidden or faded on its own, so a large assembly stays within the part limit. Nameless bodies are never copies. OpenCascade gives colors in linear RGB, converted to sRGB; parts keep the file's colors in both themes, and a part without one gets a solid's. Each part needs a color of its own for the legend, so a repeated color is shifted a step of 1/255 or two. A piece's display group names its part (`part`) rather than matching it by color, as the site's models' pieces do, so the pieces' colors need only differ. The legend's hint says which kind of parts the file has: colors, listed solids, separate solids or bodies.
- **Keeping the last file:** `lastFile.ts` keeps the last file opened in IndexedDB (which holds large files), and a reload reopens it, noted by the file name. A newer file replaces it; Close file forgets it and returns to the drop zone; a kept file that no longer opens is reported and forgotten. Storage failures (private windows, blocked site data, quota) just mean nothing is kept.
- **Downloads:** `CadViewer`'s `downloads={false}` hides its own download links, and its load errors stop pointing at them.

### Drawer cabinet

The **Drawer cabinet** at `/misc/drawer-cabinet/` is an original self-contained SCAD model: a frameless plywood case with one column of inset drawers on wooden runners. Its origin is the front-bottom-left case corner with the front face at Y=0, so its metadata sets `camera` to view the front. Drawer 1 is the top drawer. Drawers form one `Drawers` list parameter of `[front height, depth]` rows with no fixed maximum. Piece colors use signed base-7 nudges, giving 343 pieces per legend color, and drawing colors use a 1/16 grid with room for 4096 pieces, so the opening's 1-inch-per-drawer assertion is the practical limit. Zero height shares the remaining opening between those drawers; zero depth fills the case less the back clearance. Assertions require set heights to total the opening when none is zero.

`Back_fit` sets how the case back fits. In side rabbets (the default), the back sits in full-height rabbets in the sides and covers the back edges of the top and bottom, which are a back's thickness shallower; its edges show above and below. Rabbeted all round:
- **Top and bottom:** they run the full depth with a back rabbet along their inside faces, and their part sheet adds G-G, a section at the back edge.
- **Sides:** with rabbeted case joints, the end rabbets run through to the back, and they already clear a side back rabbet no deeper than they are, so that rabbet runs the full height. With butt joints, or a deeper back rabbet, the side rabbets stop inside the top and bottom's thickness so no notch shows, and the side sheet dimensions the stop.
- **Back panel:** it fits between the top and bottom rabbets with every edge hidden.

`tests/drawer-cabinet.test.mjs` checks closed, non-overlapping pieces for each runner style and case joint, including rabbets deeper than the end rabbets. It also checks the hidden edges by raycasting.

`Runner_style` selects screwed strips, strips housed in stopped case-side dados, or side-hung strips in drawer-side grooves. Supported boxes bear on the strip whose top is level with their front bottom and stop `Runner_clearance` below the strip above, which keeps them from tipping; the bottom drawer runs on the case bottom with no lower reveal. `Box_construction` selects butt-jointed boxes with full-length sides or a full-width front and back, each with a bottom nailed under or slid into a groove. A grooved bottom passes under a back that sits on it. With full-length sides, the front's groove runs through; with a full-width front, it stops under each side's inside face, and its part sheet adds M-M, a plan section through the groove at the right end, dimensioning the stop and depth. The fronts are integral and inset. Fourteen legend colors identify case members, runners and drawer roles, alternating between odd and even drawers so neighbors stay distinct. `Drawer schedule` output lists fronts and boxes to the nearest 1/64 inch, marking rounded values with ≈. The explosion is sequenced: to 100 percent the case opens and drawers slide out whole until clear; to 200 the drawers spread vertically and come apart. Drawings (`customizer.drawings`) give the assembly, a runner detail and part sheets. The drawing pass colors each physical piece uniquely with exact binary fractions, so each sheet selects one mesh, while the viewer keeps role colors. Drawer fronts, side pairs, backs and bottoms share a sheet when their finished geometry matches; signatures are rounded to a millionth of an inch. Side-hung grooves bear on their strip tops. Long part-sheet titles shrink the shared part-sheet selector instead of widening narrow pages. Case and drawer parts are plywood: `SHEET_PARTS_V1` reuses the drawing groups, and the case sides, top/bottom and drawer fronts keep their grain. The hardwood runner strips are its only `CUTLIST_V1` row. Run `bun test tests/drawer-cabinet.test.mjs tests/drawer-cabinet-drawings.test.mjs tests/sheet-layout.test.mjs`.

### SCAD drawings

For new SCAD imports, include dimensioned assembly and part/joinery sheets, an all-sheets PDF, and a cut-list worksheet/CSV for woodworking by default unless the user narrows the scope. STEP entries should receive equivalent drawings once an importer is available; STEP import is not implemented yet. STL-only entries retain viewing without invented design dimensions.

Set `customizer.drawings: true` to enable a **Drawings** section between the viewer and cut list. It supplies front, top, and right-end assembly views in third-angle arrangement, enlarged joint sections when defined, and selectable dimensioned part sheets. All sheets have source-authored dimensions, light/dark palettes, and zoom/pan. Keep opaque, themed paper behind the visible drawings for readability. `DrawingViewport` places a transparent SVG `<use>` instance behind each sheet to cast the theme-hover shadow from linework and labels only. It follows the visible scroll viewport, pan, resize, zoom, and live source SVG; it is noninteractive and hidden from assistive technology. Drawing pages apply the shared hover-shadow tokens to separate content groups so neither the paper nor its scrollbars enter the shadow. Fullscreen and reduced-motion behavior remain unchanged, and PDF export renders only the original sheet components. The assembly sheet gives overall dimensions; joint and part sheets define mating relationships, finished sizes, and machining geometry. An **Open drawings PDF** button exports every sheet using the current valid dimensions and opens it in a new tab, where the browser's viewer prints or saves it.

PDF export reuses the same SVG sheet components as the page, rendering assembly, joint detail (when present), and every grouped part sheet in order. It does not depend on the selected part sheet, 3D view, screen zoom, scroll position, viewport, or site theme. The default tote exports seven pages; unequal handle laminations produce eight. Each sheet fits one US Letter page, choosing portrait or landscape to maximize the drawing, with white paper, dark vector linework, section hatches, selectable text, page numbers, and an explicit “not to scale” note. Use written dimensions; the PDF is not a full-size template. A font-matched white box behind each dimension replaces the SVG text halo so witness lines do not cross labels.

`DrawingPdfDownload` lazily imports `drawingPdf` only when requested. PDF generation uses pinned `jspdf@4.2.1` and `svg2pdf.js@2.8.1`, with local Liberation Sans regular/bold fonts embedded for inch marks and other drawing symbols. Both PDF code and fonts load only on export; the homepage and normal CAD viewing do not request them. Font notices and library licenses ship in `/licenses/`. Generation stays in the browser; it accepts only the site's React-generated SVG from validated drawing data, with external stylesheets and images disabled. Font-load/conversion failures show a retry message. Pending, running, or invalid model edits disable the button; edits during export cancel it so a stale snapshot cannot be downloaded. Temporary fonts and download URLs are cleaned up.

Browser acceptance covers the actual downloaded files: seven/eight pages, all part titles, updated fractional dimensions and optional bores, embedded Unicode fonts, vector-only pages, stable exports across theme/zoom/mobile changes, disabled stale/invalid exports, cancellation during loading, and failure/retry. Inspect rasterized PDF pages for label clipping, hatch holes, and readability as well as checking extracted text. PDF paper-size choices and fixed drawing scales remain follow-up options.

The configured source must recognize the private `$misc_drawing = true` pass. In that pass it renders the assembled geometry independently of `Part`/`Explode` and emits exactly one `echo("DRAWING_V1", [units, views])`. Units are `inches` or `mm`; geometry and dimension witness coordinates are always millimetres. Each assembly view row is `[id, title, [rightAxis, upAxis, towardCameraAxis], dimensions]`, with unique `front`, `top`, and `right` IDs. Axes must be orthonormal. Each dimension is `[label, pointA, pointB, "horizontal" | "vertical", outsideSide, tier]`, where `outsideSide` is −1 or +1 in the projected axis and `tier` is an integer 1–4. Coordinate pairs define the measured distance along the selected view axis. Keep witnesses and derived dimensions in SCAD beside the geometry; do not duplicate model formulas in the UI.

For model-specific joint captions, append a third item to `DRAWING_V1`: `[jointTitle, description, bearingLabel]`, three nonempty strings. These captions require the two joint section views and propagate to screen headings, SVG descriptions, bearing-line titles, and PDF. Sources that omit them retain the tote's existing captions. Sheet numbering follows the actual presence of a joint sheet.

SCAD echo rounds floating-point coordinates to six significant digits. A witness-point component may therefore be a number or `[wholeMillimetres, millionths]`, decoded as `wholeMillimetres + millionths / 1000000`; both entries are integers, and millionths is between 0 and 1000000. The tote uses this encoding for dimension witnesses, bearing lines, and guides, preserving exact woodworking fractions even at large or negative model coordinates. Section depths and crop-rectangle components accept the same number-or-pair encoding. Use it for planes through precise bore centers; rounded planes can fall on the wrong side of a mesh vertex. View axes remain plain numbers.

The optional `joint-longitudinal` and `joint-transverse` views must appear together. They add a fifth row item: `[depth, crop, breaks, notes, contacts]`. `depth` locates the section plane along its toward-camera axis. `crop` is `[uMin, vMin, uMax, vMax]` in the projected plane. `breaks` names cropped boundaries (`left`, `right`, `top`, `bottom`) where continuing material receives a break mark. Notes are source-evaluated strings; each contact is a pair of 3D points marking a bearing surface. The source defines section orientation and depth for its joint: the tote cuts through a handle lamination and a riser; the frame cuts across a rail and along a stile outside the rear pocket. Each physical-part mesh is intersected with that plane, joined into closed contours, and cropped. Separate hatches distinguish parts; even-odd filling preserves holes and disconnected contours when screw bores are enabled. The highlighted contact lines follow the source-defined bearing surfaces. When a plane lies exactly on a stepped face, section topology uses the material immediately behind the plane. Welding accounts for Float32 coordinate precision, and contour simplification preserves short genuine corners.

The optional `echo("PART_DRAWINGS_V1", rows)` uses rows `[id, title, quantity, notes, sourceRGB, views]`. Each row selects exactly one colored physical mesh from the same assembled pass; missing or ambiguous color matches fail the drawing update. Its one to three views use the same axes, dimensions, and section format, with unique local IDs. A sixth view field can contain dashed reference lines as pairs of 3D witness points; use `[]` for the fifth field when no section is needed. These guides distinguish machining limits, original blank faces, glue edges, and bore axes from real mesh edges. The UI presents a main view and enlarged details at independent scales; users select a part sheet without changing the model's `Part` control.

Group identical pieces by finished geometry and quantity. The tote has five sheets by default and six when the handle laminations differ in thickness. The bottom sheet represents two resawn halves, not an extra glued panel. Side sheets explicitly mark the stopped groove's full cutting run even where its ends overlap the end dados. End sheets show inside/outside faces and the web between the opposing groove and riser housing. Optional `End_grain_screw_bores` run along X through the riser's outside face, below the slot floor, into the handle's notch-shoulder end grain. They are centered across the glued handle width and disabled by default. Diameter (5/32 inch), height (half the notch depth above the handle underside), and `Screw_embedment` (1 inch from the shoulder) remain adjustable placeholders. The riser and handle sheets dimension the bore path and blind depth; only laminations actually intersected by the pilot receive a bore detail. Drill after laminating; no screws, countersinks, or stepped clearance/pilot holes are modeled. Finished part dimensions stay separate from the cut list's rough-stock, shared-parent, resaw, and machining allowances.

`compileDrawings` runs the private pass in the same cancellable worker job as the model. The art frame supports eleven constructions in one self-contained source: half-lap, plain miter, mitered half-lap, bridle, mitered bridle, exposed-spline miter, rectangular loose-tenon miter, dowelled square corner, dovetail-key miter, blind mortise-and-tenon, and flush through mortise-and-tenon. **Conflict analysis** (`conflicts.ts`) explains a failed assertion. The engine reports only an assertion's message and drops a failed run's echoes. So a `conflicts` worker job renders a geometry-free copy of the model: its assignments and functions, with every assert (top-level, or inside top-level `for` and `if` blocks) turned into `echo("__MISC_CHECK", [index, [sub-condition results], str(message)])`. Conditions split at top-level `&&`, unless a top-level `||`, `?:` or `let` would change their meaning. One run takes well under a millisecond.

Each failing sub-condition is traced, through assignments and function bodies, to the inputs it depends on. For each input, an expanding search and then bisection find the nearest value above and below the current one that passes the check without failing a check that passed:
- Numbers search on the input's step, or a precision grid (1/16 in for inch models, 0.1 mm otherwise), within the input's range.
- Booleans and dropdowns try their other values.
- List inputs search each numeric cell within its column's range.

A search stops after 4 seconds. Asserts inside modules or functions are out of reach, so a model whose checks are there (the magnetic saw guide) keeps the plain message.

When an update fails an assertion, the form runs the analysis: precision is 1/16 for `units: "inches"`, otherwise 0.1. It shares the update's cancel signal, so a new edit stops it, and the status reads "Finding the conflicting settings…" meanwhile.
- **Highlighting:** each involved input gets `data-conflict`, `aria-invalid`, a `--cad-section` outline and a ⚠ after its label. Collapsed parameter groups holding one open.
- **Tooltip:** hovering or focusing an involved input (focus covers touch) shows a tooltip, linked through `aria-describedby`. It gives the assertion's message and the failing check, with readable operators and the current values it uses. It also gives that input's fix with its change ("Lower to 10.25 (−0.5)"; list fixes name their cell), and the other inputs involved.
- **Fix buttons:** below the status, each conflict lists one button per fix, which applies it and updates at once. A conflict with no single-input fix asks to adjust its inputs together.
- **Lifetime:** the explanation stays while editing, so a tooltip can guide the edit, and clears when the next update starts. `conflictText.ts` words the checks, values and fixes.

For clear explanations, write SCAD checks as top-level asserts (or inside top-level `for`/`if` blocks) with one concern per assertion and a message naming it. Derive intermediate values in top-level assignments so a check reads in terms of them, and keep conditions that share no concern in separate asserts. A bundled assert still splits at `&&`, but it shares one message, so its tooltip can only quote the failing part. The tool tote follows this: its handle check, once "Handle must clear sides, engage riser slots and cover riser tops", is four asserts, ending with "The handle top must reach the riser tops." Its other bundled checks are split the same way, with unchanged conditions. Checks inside modules or functions keep working but aren't explained. `tests/conflicts.test.mjs` covers:
- no model conflicting at its defaults
- the tote's shortened handle
- a per-drawer cabinet check traced to its list cell
- strict limits, ranges and `str()` messages

The mouse follows Onshape. Right-drag orbits about the grabbed point; Ctrl-, Cmd- or Shift-right-drag and middle-drag pan, holding the grabbed point under the pointer; the wheel or a pinch zooms about the point under the pointer; left-click selects, and left-drag does nothing. On touch, one finger orbits and two fingers pan and zoom. The browser context menu is suppressed on the canvas. The pivot is the point on the visible, unclipped part under the cursor. Failing that, it's a snapped corner or edge, and otherwise the current center. The camera and its target rotate rigidly about the pivot, yaw about Z then pitch about the view's horizontal axis, so the pivot stays under the cursor without the view jumping. Rotation speed and the pole limits match the orbit controls, and a marker shows the pivot while dragging. Panning and zooming hold a point under the pointer too: the point it's on, found as the pivot is, or over empty space the point on its ray at the target's depth. Panning (`panTo`) slides the camera and its target across the view until that point is under the pointer again; zooming (`zoomAbout`) moves them toward it or away by the same factor, so it stays put on screen. Two fingers hold the point between them where they land, panning as they move together and zooming as they spread or pinch. Wheel steps keep the orbit controls' rate, a trackpad pinch (Ctrl without the key held) ten times as fast, and the camera keeps its distance limits from the target. The orbit controls' own rotation, panning and zoom are disabled; they keep the camera's target and distance limits, capture the pointer for drags and suppress the context menu. A second finger hands orbiting over to the pinch. When a pinch ends with one finger still down, that finger orbits again about the point under it rather than panning against the lifted one, and only a lone finger's tap selects. The arrow keys still orbit about the center.

The view is orthographic by default, as Onshape's is, so the named views are true elevations and parallel edges stay parallel; the Perspective checkbox by the Display menu switches to a 35° perspective, and Reset view keeps the choice (`perspective` in `ViewSettings`). The choice is kept in this browser for every model and visit (`localStorage`, `cad-projection`, set only for perspective); where storage is blocked, it lasts for the page. The perspective camera stays the eye that orbiting, panning, zooming and the named views move. When orthographic, an orthographic camera copies its view (`lens`) each time the scene is drawn, picked or projected, seeing as much as the perspective camera does at the target's distance: moving the eye nearer zooms, and the point under the pointer stays put, as zooming about it moves the eye and target toward it by one factor. It sits well back along the line of sight, so the model is always in front of it. Picking and snapping raycast through it; hidden-corner checks look straight along the view rather than from the eye, and the section handle's size uses a pixel's size at the target, the same at every depth.

An **orientation cube** (`viewCube.ts`) sits at the top right of the 3D view and turns with the camera. Z is up and the front faces −Y, so its faces read Front, Back, Left, Right, Top and Bottom.

  - **Named views:** cube picks and named views (`orient()`) end upright with Z up, in the standard orientation: a top view has the front at the bottom, a bottom view at the top.
- **Rendering:** the faces are HTML with CSS 3D transforms recomputed on every render from the camera's rotation, so the browser does the hit testing. Hidden faces turn away with `backface-visibility`.
- **Axes:** an X/Y/Z axis triad (red, green, blue) below the cube fades axes that point away.
- **Arrows:** as in Onshape, four arrows around the cube turn the view 90° about the screen's horizontal and vertical axes, toward the side they point to: from the front, right shows the right side and up shows the top. They keep going: up from the top shows the back, upside down. The two curved arrows above roll the view 90° clockwise or anticlockwise about the line of sight.

The **section view** works as in Onshape (`section.ts`). The Section menu cuts the model by a default plane or by a face. The default planes pass through the model's origin and are Onshape's: Front (XZ, facing −Y), Top (XY, facing +Z) and Right (YZ, facing +X). Choosing **Face…** waits for a click on a face (crosshair cursor, Cancel or Escape to stop), and the plane runs through the clicked triangle with its outward normal, with float error dropped so faces square to the axes stay square. With a face selected, the menu offers **Selected face** in Face…'s place, and choosing it, turning the section on with Shift+X, or Add plane cuts through the selected face (the last clicked) at the point clicked, as picking it would; Add plane falls back to a default plane once a plane already passes there. Material on the normal's side is removed, so the cut is seen looking back along the normal; **Flip cut** removes the other side.
- **Point and depth:** a section has a point, where its manipulator sits: the model's centre for a default plane, the clicked point for a face. Depth is the point's distance from the reference plane along its normal, in the model's units: a slider across the depths that cut the model's bounds, and an exact field that also takes values beyond them. Setting it moves the point along the reference normal, keeping any tilt. Depths through a default plane can be negative, as the Front plane faces −Y.
- **Tilt:** the plane through the point can tilt about the reference plane's two in-plane axes (`planeAxes`): the second as near to up (+Z) as the plane allows, or +Y for a plane facing up or down, so Front tilts about X and Z, Top about X and Y, and Right about Y and Z. The normal turns about the first axis, then the second, so the first axis turns with the second and stays in the plane. The tilt fields name the axes (or "the first/second axis" for a slanted face), take degrees, and **Square up** clears them. The stage label adds any tilt.
- **Manipulator** (`scene.ts`), as in Onshape: an arrow at the point toward the removed side, and two arcs beside it about the tilt axes, in amber (`--cad-handle`) with a dark outline so it stands out against the cut faces, the model and the page, and lighter while hovered or dragged. A left button or lone finger on it takes over from picking and orbiting, with pointer capture; each handle has a wider invisible copy to grab. Dragging the arrow follows the point on its line nearest the pointer's ray and moves the section's point along it; dragging an arc follows the pointer's ray meeting the plane square to its axis, ignoring rays nearly in that plane, and tilts to a tenth of a degree. Drags report their change from where they began (`HandleDrag`), so the viewer applies each to the section as it was when the drag started. Clicking the arrow without dragging flips the section.
- **Several planes:** as in Onshape, up to three planes (`maxSections`) cut at once. **Add plane** adds the first of Front, Right and Top not yet used, so a second plane makes a corner cutaway, and makes it active. Numbered buttons choose the active plane, which the Section menu, the fields and the manipulator edit, and × removes one; Off in the menu removes them all. Only material on the removed side of every plane is removed (Three's `clipIntersection`), so two planes cut away a quarter and three an eighth. For each plane, each piece counts its own stencil with only that plane clipping (a drawing of just its triangles, sharing the model's buffer), then draws its own cap, kept by the other planes turned around so it fills only where they remove material, and clears the stencil; the passes draw in turn between the model and its edges. So pieces that touch keep their own cut colors and the joints between them show. A cap is the piece's color brightened, a fifth of the way to white in linear light, so cuts stand out from the model's lit faces while keeping their parts' colors, and hatched with diagonal lines darker (0.6) every 7 pixels on screen, as sections are in drawings, so a cut reads as one in any color, including a one-color model's; it's tinted when its piece is selected or hovered, as the piece's faces are. In Solid + edges, each plane also outlines its capped pieces' cuts in the edge color (`outlineCuts`): the segments where it crosses their triangles, rebuilt as the plane moves, a hair toward the removed side so they show in front of the caps, and kept by the other planes as the caps are. So pieces of one color that touch, such as a part's pieces, still show their joint. A cap covers only the square around the disk where the plane crosses its piece's bounding sphere, so caps fill no more of the screen than their pieces, and a piece a plane misses draws no count or cap; this keeps a many-piece model's three-plane cut within about a fifth of the single-cap cost. Each plane cuts a hair (a ten-thousandth of the model's radius) past where it's set, so a face lying exactly on it is removed instead of flickering against the cut of the piece behind, as where the tote's centre plane meets the seam between its handle laminations; depths read as set. The stage label numbers the active plane ("2 of 3").
- **Uncut parts:** **Leave selection uncut** (models with a legend) adds the selected parts and pieces to those left whole (`ViewSettings.excluded`): they skip clipping and caps, and picking, measuring and occlusion treat them as whole. Each is listed with × to cut it again. Reset view clears the planes and the uncut parts.
- **Keys:** N (or View normal) looks back along the active plane's normal at the cut face on; Shift+X turns the section off and back on, restoring the last planes, depths and sides (or the Front plane through the middle).
- **Scene:** `ViewSettings.sections` are planes in model coordinates (`normal · p > constant` is removed). The scene turns each into a Three clipping plane in its centered coordinates and places each piece's cap on it. Picking, hover, measuring and occlusion skip clipped-away material, and every click reports the face under it (`PickedFace`) for picking a section face.
- **Units:** depths are scene millimetres, shown in the model's units; a visitor's change of units rescales the section with the model. The stage label names the plane and depth.
- `tests/section.test.mjs` covers the default planes, flipping, face planes, depth ranges, the tilt axes and tilting about the section's point.

Edges and vertices are selectable too. `topology.ts` joins each piece's drawn crease segments into whole edges. Joins happen through points where exactly two segments continue straight on, or along a tessellated curve: equal-length segments turning less than 20°, so an OpenSCAD circle is one closed edge. Corners, T-junctions and kinks between unequal segments end an edge, as in a B-rep model, and edge endpoints are the vertices. Some exporters (SketchUp's, for one) write meshes whose faces split a shared edge at different points, so it arrives as overlapping segments that meet three at a point; collinear segments that overlap are first made one run, cut at every endpoint along it, each piece once (`runs`), so such an edge is still whole. Picking snaps to a vertex within 8 px, else an edge within 6 px, else the face under the pointer. A candidate must be on a visible piece and the kept side of a section. A raycast to its snapped point rejects it if opaque material is in front; hidden and translucent parts never occlude. Selected and hovered edges draw as wide lines (Three's `LineSegments2`), vertices as round markers, in the selection and hover colors. Hovering an edge marks its part's legend entry. Edge and vertex keys carry a geometry version, so regenerating drops them rather than pointing at a different edge. They join the multi-selection with labels such as "Edge · Case top". Appearance actions apply to selected parts, and keyboard shortcuts treat a selected edge or vertex as its part. `viewer.entity(key)` returns its owner and model-coordinate points or position for measurement. `tests/topology.test.mjs` covers compiled boxes, slots, circles, hexagons, T-junctions and kinks.

Faces are selectable too, as in Onshape: a click away from any edge or corner selects the face under the pointer (`face:<version>:<layer>:<index>`). A face is a STEP file's own face, or else a region of a piece's triangles bounded by the creases drawn as its edges (`faceRegions` in `topology.ts`: triangles join where their sides overlap along a line, as a shared side does or as a T-junction's do, meeting at under 25°), so a box has six faces and a smooth cylinder's side is one. Selected and hovered faces draw over the model half see-through in the selection and hover colors, cut as their parts are. A selected face reads "Face · part" and stands for its part: the panel's opacity, Hide, Isolate, Ghost others and Leave selection uncut, and the Y, Shift+I and Shift+T keys, act on it, though the legend doesn't mark the part selected. Models without a legend select faces too. Faces are measured as in Onshape (`measure.ts`): one face gives its area (in mm² and in², the model's units first), three or more their total area. With another face, edge or vertex, a face gives the shortest distance, between its triangles' closest points (pairs too far apart by their bounding spheres are skipped), with a dimension line; two flat faces add their angle, or their spacing if parallel and it differs from the distance; a flat face and a vertex add the distance to the face's plane; a flat face and a straight edge add their angle, or their spacing if parallel. A face's triangles, area, centre and normal (when all its triangles share one) are kept per key until the model changes, and the measurement is worked out once per selection.

Selected edges and vertices are measured automatically, as in Onshape (`measure.ts`, model millimetres):
- **One edge:** its length. A closed edge whose points are equidistant from their centroid, like an OpenSCAD circle, gives its diameter and circumference.
- **Two vertices:** the distance plus ΔX, ΔY and ΔZ.
- **A vertex and an edge:** the minimum distance, plus the distance to a straight edge's line when that differs.
- **Two edges:** the minimum distance. Two straight edges also give their angle, or the perpendicular spacing when parallel.
- **Three or more edges:** their total length.

A readout panel at the stage's top-left lists the rows in the entry's units with the other unit alongside. Inches snap to 64ths when within 2e-5″, which absorbs Float32 mesh error; angles use degrees. A lone vertex or an unsupported mix gets a hint instead. In 3D, a magenta dimension line with end markers joins the measured points, drawn over everything. An HTML label with the first value sits at the anchor and is re-placed after every render. Selected parts are not measured. Curved edges are measured on their facets, so their lengths approximate the true curve. `tests/measure.test.mjs` covers each case.

Onshape-style shortcuts work from the 3D view or the legend panel, or with nothing focused while the pointer is over the model, and never while typing in a field. Shift+1 to Shift+7 give the front, back, left, right, top, bottom and isometric views on every model, with or without a legend. Y hides. Shift+Y shows the hidden targets, or otherwise every hidden part while keeping fades. Shift+I ghosts everything else and restores it when pressed again. Shift+T toggles between 30% and full opacity. Space (from the 3D view) clears the selection; as in Onshape, Escape does not. There, Space is always the viewer's: it never scrolls the page, even with nothing selected. Elsewhere on the page it keeps its usual meaning (scrolling, typing, pressing a keyboard-focused control). The 3D view's focus ring shows only when it is reached from the keyboard: a click or tap marks the canvas (`data-pointer-focus`) until it loses focus, so keys pressed after clicking the model don't flash an outline. Mouse use of the viewer's own controls hands focus back to the 3D view the same way. That covers buttons, checkboxes, sliders and headings in the toolbar, display controls and legend panel, the panel headings, and dropdowns the pointer opened. So after clicking Fullscreen, Hide or a legend entry, Space clears the selection instead of pressing that button again, and the other shortcuts work. Keyboard activation (a click with `detail` 0, or a dropdown changed with the arrow keys) keeps focus where it is, as does the parameter form, whose fields and inline actions manage their own focus. Keys act on the selection; with nothing selected, they act on the part or piece under the cursor, raycast only when a key is pressed. The buttons expose these via `aria-keyshortcuts` and tooltips. Escape only exits fullscreen. Uncolored STL entries, and visitors' files without several colors or solids, have no legend or parts, so only Space and the named views apply there; their edges and vertices are still selected for measuring, and the help text says so.

Pieces that share a legend color can still be selected individually. The source gives each physical piece its own `color()` within 3/255 per channel of the legend color. The viewer maps any group within that tolerance to the nearest legend entry, and displays it in that entry's exact light and dark colors. Each exact source color (`#rrggbb`) is a separate piece. Optional `echo("PIECES_V1", [["#rrggbb", label], ...])` names pieces; unnamed ones fall back to "legend label · n". Clicking in 3D toggles the single piece; a legend entry toggles the whole group. Selecting a group absorbs its selected pieces, and clicking one piece of a selected group leaves its other pieces selected. A lone selected group's panel lists its pieces so they can also be chosen from the keyboard, and a lone piece's panel offers **Select all**. A piece's own setting overrides its group's, and a group-wide change replaces its pieces' settings. A single-piece legend entry behaves exactly as before. The drawer cabinet uses this for its drawer members and runner strips; its drawing pass keeps separate exact-fraction colors.

Optional `customizer.cutList: true` (with `units: "inches"`) replaces plain console output with a woodworking worksheet below the viewer. Its source emits one `echo("CUTLIST_V1", rows)` with rows shaped as `[id, name, material, quantity, finishedThickness, finishedWidth, finishedLength, blankKind, optionalResawGroup]`. SCAD supplies the evaluated blank dimensions; the UI groups equal blank kinds, materials, dimensions, stock thickness choices and preparation modes, sums quantities, and retains the physical IDs for paired color swatches. The tote defaults to five rows of two finished blanks. The ends and risers each share one parent for crosscutting, the bottom uses one resaw parent, and the sides and handle laminations use two parents each. Unequal handle laminations split automatically; stock entries follow their physical pieces through splitting and regrouping. Do not add aggregate glued panels as extra cut-list items.

The CSV title and filename identify the current Misc item. Resaw controls and CSV notes appear only when the source contains resawn parts. The worksheet and CSV contain part names, separate finished/rough quantities, grouped finished/rough dimensions, and rough board feet per row and in total. An optional ninth cut-list value identifies two matched halves resawn from one parent board; members must share the same dimensions and group into quantity two. The bottom halves use `bottom-parent`; handle laminations remain separate solid-wood pieces. A resaw row has finished quantity two and rough quantity one, with parent width equal to one half’s width plus allowance, never the assembled panel width.

Optional `echo("CUTLIST_STOCK_V1", [millingMinLength, sawMinLength, resawKerf, resawCleanupPerHalf])` supplies positive inch defaults for adjustable worksheet controls. The tote defaults are 14 inches for jointer/planer stock, 10 inches for table-saw stock, 1/16 inch bandsaw kerf and 1/16 inch cleanup thickness per half. Machine minimums apply to **parent stock during jointing, planing and ripping**, before crosscutting shorter blanks. Finished dimensions remain unchanged.

For each ordinary matching row, Auto compares separate parents against a single shared parent and selects sharing only when it uses less total stock length. With `blankLength = finishedLength + lengthAllowance`, separate stock has `quantity` parents of `max(blankLength, millingMinLength, sawMinLength)` each; shared stock has one parent of `max(quantity × blankLength + (quantity − 1) × crosscutKerf, millingMinLength, sawMinLength)`. The crosscut kerf defaults to an adjustable **⅛ inch** and is distinct from the bandsaw resaw kerf. The 1-inch length allowance remains **per blank**. Each row offers Auto, Separate blanks or One shared board and displays how many blanks each parent yields. S3S the shared parent, then crosscut it; the default ends use one 18⅛-inch parent yielding two 9-inch blanks for the 8-inch finished ends. Risers share one 23⅝-inch parent yielding two 11¾-inch blanks. Separate mode retains the old 14-inch-per-blank option. This is a comparison within matching rows, not cross-row nesting or a general cutting-stock optimizer. Resaw parents keep their existing one-board/two-halves calculation and never acquire a crosscut kerf.

A resaw parent’s minimum milled thickness is `2 × (finishedHalfThickness + cleanupPerHalf) + kerf`; the default ¼-inch bottom therefore requires 11/16 inch after milling and before resawing. The worksheet adds an adjustable **¼-inch total jointing/planing thickness allowance** (both faces together), once per rough blank or resaw parent. Auto rounds that required rough thickness up to the next buying size from **4/4, 5/4, 6/4, 8/4, 10/4, 12/4, 16/4** (1, 1¼, 1½, 2, 2½, 3, 4 inches). See the [supplier’s explanation of quarter sizes](https://www.woodworkerssource.com/blog/woodworking-101/tips-tricks/what-does-44-mean-when-talking-about-lumber/). A row can explicitly select thicker stock; an override that becomes undersized after a parameter edit stays visible and blocks CSV export until corrected or returned to Auto. Explicit and automatic choices remain distinct through grouping, even when they currently resolve to the same size. Requirements above 16/4 have no automatic selection and also block export. Width/length allowances default to ½ and 1 inch. Negative, empty or nonfinite machining allowances are invalid; zero is allowed. A visible resaw note and CSV preparation notes explain the milled target, added surfacing thickness and one-board-to-two-halves relationship.

Board feet use `parentQuantity × nominalStockThickness × parentWidth × parentLength / 144`; machine minimum lengths and machining allowances are included, and each shared or resawn parent is counted once. An adjustable **20% extra-board-feet allowance** covers board layout and defects. Show the base board feet and a **With N% extra** column containing `baseBoardFeet × (1 + percentage / 100)` for each row and both totals. Display values to two decimals, using unrounded values for the calculations. The percentage can be zero or fractional; negative, empty, nonfinite, or overflowing values block CSV export and suppress the adjusted totals. CSV includes parent dimensions, quarter-size labels, preparation/yield notes, both unrounded board-foot columns and totals, the selected percentage, and all worksheet allowances including the crosscut kerf. Defaults total 4.55 base board feet and 5.46 with 20% extra. There are no cost columns or supplies section.

Worksheet overrides affect stock planning only; they persist through model/theme changes and `Show_cut_list` toggles for the current page session, but do not change the finished SCAD geometry or its configured source. They reset on reload unless saved with a configuration. Source defaults live in the hidden stock-preparation variables and also appear in native OpenSCAD console output. Pending/failed model updates mark retained tables as previous settings and disable CSV export.

Generated files open in a new tab rather than downloading (`openFile.ts`), so they can be printed straight away or saved from there.
- **PDFs** (drawings and sheet layout): the tab opens from the click itself, so pop-up blockers allow it. It shows "Preparing…" until the PDF loads in the browser's viewer, whose toolbar prints and saves it. A failed or cancelled PDF closes the tab.
- **CSVs** (cut list and sheet layout): they open as a printable table page, with **Download CSV** (saving the file under its own name) and **Print**. Both buttons are hidden when printed.
- **Pop-ups blocked:** if the browser blocks the tab, the file downloads instead, and a status line says so.

STL and OpenSCAD source links still download: a browser can't show an STL, and both are for other programs. Header grid lines have contrasting light/dark tokens; narrow layouts scroll the table without widening the page.


### Sheet layouts

Optional `customizer.sheetLayout: true` (with `units: "inches"`) adds a **Sheet layout** section for sheet goods. Plywood parts are laid out on full sheets instead of entering the board-feet cut list. The source emits one `echo("SHEET_PARTS_V1", rows)` with rows `[id, name, material, quantity, thickness, width, length, grain, legendIds]`. Dimensions are finished inches. `grain` is `"length"` when the part's face grain must run along its length, or `"any"` when the part may turn. `legendIds` lists `customizer.parts` IDs for swatches and diagram colors. Optional `echo("SHEET_STOCK_V1", [sheetLength, sheetWidth, kerf, edgeTrim])` sets the editable defaults. Without it the worksheet uses a 96 × 48 inch sheet, ⅛ inch kerf and no trim. A model can use both contracts: the drawer cabinet lays out its plywood and lists its hardwood runners in the cut list.

Parts are grouped by material and thickness and keyed A, B, C… in source order. Face grain runs along the sheet length. **Grain** lets visible parts keep their grain while hidden parts turn, lets every part turn, or keeps every part aligned. **Densest nesting** is a guillotine packer: every free region is split by a straight through-cut, so layouts can be cut on a table or track saw without plunges. **Rip first, then crosscut** rips full-length strips, then crosscuts each strip. A part narrower than its strip is trimmed to width last. Parts fill partly used, wider strips (trimmed to width) before a new strip is ripped, so the strips take as little of the sheet's width as they can and leave the widest offcut. For example, the drawer cabinet's 1/2″ sides and backs for six drawers take four strips, 17.1354″, rather than one strip per part width, 25 3/8″. Both methods add kerf after each part and try several orderings and split rules. They keep the result with the fewest sheets, then (ripping first) the least width ripped, then the least trimming waste, then the emptiest final sheet. Each sheet gets a themed SVG diagram with rip lines, trimmed offcuts and turned parts marked; rip-first sheets also list each strip's crosscuts. A part that cannot fit the usable sheet in an allowed orientation produces an error instead of a layout. The CSV records the settings, sheet counts, part keys and every placement. Pending, failed or invalid settings disable it. **Open PDF** lays the layout out two sheets to a US Letter portrait page (`sheetLayoutPdf.tsx`, loaded on demand). Each page has:
- **Header:** the item title and settings.
- **Sheets:** each sheet's caption with its share of the sheet area, then its diagram. A rip-first sheet also lists its strip-by-strip cuts and trims.
- **Key:** the keys of the parts on that page with their sizes, and a legend.

Diagrams share what's left of each page after the text, so densest layouts, which have no cut lists, print larger. Parts too small to label legibly show only their key. Like the drawings PDF, it embeds Liberation Sans, measures text with it, and sets every colour explicitly (`SheetLayoutPages.tsx`, `sheetLayoutPrint.ts`). It is disabled with the CSV, and a changed layout cancels one in progress. `tests/sheet-layout.test.mjs` independently checks bounds, kerf gaps, counts, grain and strip structure.

Versioned machine-readable echoes (`*_V1`) are filtered out of the `outputLabel` panel, which shows only the source's human-readable output.

Optional CAD `displayModel` names a local `.json` asset containing `{ version: 1, positions, normals, groups }` in millimetres. It saves the engine’s colored triangle groups for immediate display without waiting for WebAssembly or SCAD compilation. Entries without it still load their STL. The downloadable STL is unchanged. If the colored asset fails to load or validate, the viewer keeps the colored static thumbnail and error state instead of silently switching to a monochrome mesh.

Regenerate it from the default SCAD whenever geometry or source colors change:

```sh
bun scripts/export-cad-display.mjs public/misc/tool-tote/tool-tote.scad public/misc/tool-tote/tool-tote-display.json
```

The exporter uses the pinned engine and the browser’s preview validation. The tote regression test compares the saved positions, normals and groups against a fresh source compilation so the initial display cannot drift from the live model. Cold-load browser checks delay or fail the engine request and verify that the first interactive model already has its part colors in both themes.
